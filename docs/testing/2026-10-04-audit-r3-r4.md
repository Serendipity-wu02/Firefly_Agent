## 1. 背景与范围

验证范围是 shell 结果语义及启动前取消，覆盖实际 shell → shared executor → dispatcher → scheduler/round → ledger/events。R1、renderer、迁移、真实用户资料、记忆激活、CI 和依赖变更不在范围内。

原 shell JSON 在不支持的 shell、Bash 不可用、危险操作拒绝、spawn/setup 错误与非零退出时缺少 `success:false`，导致 `legacyFailure` 记录 `succeeded`，可能产生成功缓存和绿色生命周期事件。R2 已在解释器/sandbox await 后及两条启动路径前调用 `assertAllowed`，包含取消、有效计划与精确调用审批检查；该 guard 不需要替换。

## 2. 已记录实现与责任边界

- R3 在 shell 来源产生明确的成功/失败、category、retry 与 effect facts。自然退出的非零或 null 状态可能伴随部分副作用，因此 executor 记录 failed + unknown effects；dispatcher 发出 unknown，scheduler 停止并保留不确定性，不写成功缓存。
- 启动前拒绝/setup/spawn 失败为 `not_applied`。启动前取消与已启动后的 timeout 分开处理。
- `stdout` 保持 shell JSON 最后一个字段；stdout/stderr 与退出事实在共享规范化后保留。缺少显式 timeout 元数据的旧工具沿用既有默认值。
- R4 的 deferred 测试分别覆盖 permission、interpreter resolve、sandbox wrap、spawn-spec 边界，含 scheduler 已返回 cancelled 后 setup 才结束的场景；foreground/background 均不得启动。收紧 plan/approval 后仍拒绝 launch。
- 已启动 background job 继续使用独立 stop/deadline/quit 生命周期；turn cancellation 不追加杀死已启动后台任务的 signal。

## 3. 验证计划与历史结果

测试环境为 Windows、Node 24.19.0、npm 11.17.0，使用已核验 Bash fixture、专用 TEMP/TMP。依赖来自相同已验证产品版本的已安装副本，未完成全新联网安装；受限环境无法读取 npm cache。原始日志保留于当时仓库外的专用证据目录，不表示已纳入仓库。

shell outcome 与旧 timeout 兼容回归均先复现行为失败。修复后分别验证明确失败事实与缺失 timeout 元数据的兼容默认值，没有把模块加载失败或旧工具字符串当作成功依据。

独立只读审查覆盖变更源码/测试、调用者、历史及失败路径，无 Critical/Required 代码发现。确认 R2 guards 为既有行为，shared executor 有 firefly-agent 与 dispatcher 两个生产入口，`run_verification` timeout 兼容性已检查。shell 字段是权威失败元数据，不以 stdout 字符串匹配判断。
