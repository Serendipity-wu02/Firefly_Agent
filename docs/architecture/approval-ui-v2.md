# Approval UI V2

## Ownership

`ApprovalService` remains the only owner of `ApprovalRecord` state. `ApprovalPresentationCoordinator` stores only the currently displayed request ID, expiry timer, and selected surface. It does not authorize, evaluate Sandbox policy, create grants, or execute tools.

## Hybrid presentation

The coordinator checks the real Chat `BrowserWindow` state through `WindowManager`:

- the window exists and is not destroyed;
- the renderer has finished loading;
- the window is visible and not minimized.

When all conditions hold, the request is sent to the Chat renderer as a compact inline card. Otherwise the singleton compact Approval window is opened. Surface changes clear the old surface before presenting the new one, so one request is never intentionally shown in both places.

Both surfaces use the same typed preload API and resolve through the same coordinator and `ApprovalService`. Settled records (`APPROVED`, `DENIED`, `CANCELLED`, and `EXPIRED`) clear the inline card or close the fallback window. A stale resolve response clears the inline presentation instead of leaving a zombie card.

The inline card displays only structured fields from `ApprovalRequest`: requester, summary, reason, capability, the existing `risk` and `sideEffect` metadata, and effective Sandbox scope. The fallback Approval Window shows the same fields. It does not parse raw tool arguments. The current production target is `music.control`; its operation and `QQMusic` desktop target are represented by the summary, capability, metadata, and effective scope.

Approval is presented exactly once. Chat inline is preferred when Chat is
ready; otherwise the existing singleton Approval Window is used. The Pet
notification channel currently carries `PET_PROACTIVE_LINE`, which is a
speech-triggering presentation event rather than a pure approval notice, so it
is not reused for authorization decisions. No speech-panel refactor is part of
this contract.

## Firefly hint

The fallback window has the deterministic presentation copy `这个操作需要你的许可，我会等你决定。`. It is decorative UI copy only. It is not generated by the model, sent to TTS, persisted to chat history, or used as a security decision. The structured approval facts remain the authority.

## Scope limits

The Approval presenter does not own authorization or execution. Current
production requests are created by the existing Harness authorization path and
resolved by the same main-process `ApprovalService`. The Chat quick permission
switcher and Settings both write the one canonical permission scheme through
`SETTINGS_SAVE`; neither creates a second store or policy engine. The four
schemes are `READ_ONLY`, `RESTRICTED_SCOPE`, `ASK_EVERY_TIME`, and
`FULL_ACCESS`, superseding the earlier product-planning five-level vocabulary.
