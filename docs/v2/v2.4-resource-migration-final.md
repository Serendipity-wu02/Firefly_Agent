## 3. `firefly.yaml` 兼容性机制专项审查 (Special Investigation)

### 3.1 为什么 NTFS Hardlink 不能作为 Git 仓库保障？
- Hardlink 仅是本地 NTFS 文件系统层面的 inode/MFT 引用计数。
- **Git 协议完全不保存 Hardlink 关联**。当执行 `git commit` 时，Git 会将其作为独立的 blob；当其他开发者或 CI 执行 `git clone / git checkout` 时，Git 会写出两份完全独立的普通文件。一旦修改其中一份，另一份不会同步，直接造成 **双份真源污染 (SSoT Violation)**。

### 3.2 方案实测与客观比较报告

#### 方案 1: Git Symbolic Link (`resources/firefly.yaml -> persona/firefly.yaml`)
- **测试结果**: **在 Windows 平台不可行 (FAILED)**
- **原因分析**:
  1. Windows 下 Git 默认配置为 `core.symlinks = false`；
  2. 当 `core.symlinks = false` 时，`git clone` / `git checkout` 会将符号链接检出为只包含 20 字节目标路径字符串（`persona/firefly.yaml`）的**纯文本文件**；
  3. Node.js `fs.readFileSync("resources/firefly.yaml")` 读取到的是该 20 字节字符串，调用 `yaml.load()` 返回纯字符串而不是人设对象，直接导致依赖旧路径的代码崩溃；
  4. Node 原生 `fs.symlinkSync` 在 Windows 非管理员/非开发者模式下执行直接抛出 `EPERM: operation not permitted`；
  5. `npm pack` 会打包该 20 字节文本文件，导致 npm 安装用户无法正常运行。

#### 方案 2: 保持 Root 为唯一物理 Canonical 文件 (`resources/firefly.yaml`)
- **架构机制**:
  - `resources/firefly.yaml` 保持在 `resources/` 根目录物理位置；
  - `resources/persona/` 目录不存放第二份物理 YAML 文件；
  - `PersonaLoader` 与运行时系统直接将 `resources/firefly.yaml` 作为最高单一真源；
  - 全工程所有消费者统一直接读取 `resources/firefly.yaml`。
- **验证结果**:
  - **Git 可复现性**: 100% (Windows/macOS/Linux 无任何符号链接/权限要求)；
  - **npm 打包分发**: 100% (`npm pack` / `npm install` 自动包含并立即可用)；
  - **Single Source of Truth**: 100% (全局只有 1 份物理 YAML，0 副本)；
  - **物理结构影响**: 在 Manifest 中将 `firefly.yaml` 的权威归属明确为 `resources/firefly.yaml` (Root Canonical Persona Source)。

#### 方案 3: 全链路统一收敛至 `PersonaLoader` (No Physical Root Fallback)
- **架构机制**:
  - `resources/persona/firefly.yaml` 作为唯一物理文件；
  - 根目录 `resources/firefly.yaml` 物理删除，不保留任何影子文件或符号链接；
  - 全工程（所有 TypeScript 代码、测试用例、CLI、打包配置）统一调用 `PersonaLoader.resolveYamlPath()` / `PersonaLoader.getProfile()`，禁止任何硬编码相对物理路径。
- **验证结果**:
  - **Single Source of Truth**: 100% (只有 `resources/persona/firefly.yaml`)；
  - **Git / npm**: 100% 可行；
  - **注意**: 任何绕过 `PersonaLoader` 直接尝试用静态字符串 `resources/firefly.yaml` 读盘的外部工具将返回 `ENOENT`。
